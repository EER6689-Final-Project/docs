\chapter{Literature Review}
\label{chap:literature-review}

Browser performance diagnosis draws on metric definitions, instrumentation, repeated measurement and methods for retaining or selecting execution evidence. Existing systems establish several combinations of these mechanisms. The remaining question is whether evidence from a later browser visit can correctly identify an earlier cause under the proposed budget, deadline and independent labelling rules.

\section{Browser Performance Metrics and Semantics}

A performance endpoint and a diagnostic signal serve different purposes. Largest Contentful Paint (LCP) records the render timing of an eligible largest content element; it does not mean that a page is complete or that a particular resource caused a delay. Interaction to Next Paint (INP) summarizes responsiveness across qualifying interactions and depends on an input actually occurring; it cannot be inferred from a load-only visit. Cumulative Layout Shift (CLS) aggregates eligible layout instability according to session-window rules, rather than summing every shift over a page's entire lifetime. These definitions are provided by the metric specifications, guidance and implementation documentation \parencite{6WVYFE8R,B8XNKSHY,R2U9EAFA,GYN22PP7,N33VTKAN}.

Other metrics describe different aspects of performance. First Contentful Paint (FCP) describes an earlier rendering milestone, Total Blocking Time (TBT) is a lab diagnostic over a specified interval, Speed Index (SI) is based on visual progression, and client-observed Time to First Byte (TTFB) describes time to the first response byte \parencite{84ZFNR74,QHUCFVBF,A8GDSSI7,JJWRMF5Z}. For a navigation, the start point matters: an interval from navigation start to \texttt{responseStart} includes work before the request, while an interval from \texttt{requestStart} has a narrower scope. The exact navigation formula, redirect handling and cache context will be fixed in the measurement contract. TTFB is not an isolated measure of server CPU time \parencite{JJWRMF5Z,9V33RJH6}. Subresource request phases will be recorded separately using Resource Timing, whose fields and access restrictions have their own definitions \parencite{NXHCE5SV}. Event Timing and the Layout Instability API describe underlying browser observations; they are not interchangeable with the final aggregate reported to users \parencite{I8L7FN9V,R2U9EAFA}. The cited specification editions include the LCP Working Draft of 26 August 2026, Paint Timing Working Draft of 2 October 2026 and Navigation Timing Level 2 Working Draft of 1 September 2026. These definitions still require a fixed implementation and measurement contract. The proposed evaluation will begin with pilot LCP as its primary endpoint; INP and CLS remain exploratory unless a qualifying journey and finalization rule are validated.

Each metric will be recorded with its definition and version, eligible navigation or interaction, observation and finalization window, browser context, export behavior, scope and missingness reason. A missing interaction or unsupported API is not a zero. Metric attribution can offer a candidate element or phase without proving the injected fault caused the result. The web-vitals v5.1.0 attribution documentation establishes a legitimate source of original-visit diagnostic fields; it is a reference release, not the selected runtime build or a cause oracle \parencite{N33VTKAN}. FP-0.1 proposes LCP as the pilot endpoint and a median plus max(100 ms, 3 times unscaled median absolute deviation) alert threshold. These are project choices to qualify and lock before comparison, not externally validated standards. Exact runtime field mapping and finalization still require conformance checks; main-study thresholds and aggregation remain to be frozen separately.

\section{Browser Instrumentation and Measurement Effects}

A summary metric retains less execution detail than many forms of trace collection, but the difference depends on the fields actually recorded. Browser application programming interfaces (APIs), including the Performance Timeline, offer typed entries and observer/buffer mechanisms; Event Timing, Long Tasks, and Long Animation Frames (LoAF) expose particular classes of activity. The Chrome DevTools Protocol (CDP) tracing domain exposes trace events subject to implementation and lifecycle details \parencite{REP5RHB6,I8L7FN9V,KEJFZJHV,6SJEG5G9,63QKVL86}. The cited Performance Timeline edition is the Candidate Recommendation Draft of 21 May 2025. Its buffering mechanisms are finite and entry-type specific; runtime support will be checked rather than inferred from the specification. These sources justify specifying event types, timestamps, ownership, observer start time, buffer capacity, export, truncation and loss. They do not by themselves establish that the collected fields distinguish the study's fault classes or that collection has negligible cost.

In this study, “lightweight” and “detailed” will identify capture contracts. Each contract will specify the collector, entries or profiles retained, start and stop times, retention limits, export size, loss handling and resource costs. This is particularly important for a retained-original-event arm. A bounded buffer can be useful only if it starts in time and contains the needed discriminator before overflow, page termination, or export. Hindsight demonstrates finite-horizon original-event retention and retrieval for distributed systems; it motivates a feasibility test but does not prescribe a browser buffer size \parencite{3ED3FDXH}.

Instrumentation also changes what is measured. Mytkowicz and colleagues show that apparently innocuous measurement choices can produce misleading performance data in systems experiments \parencite{IWCIN2C5}. That work motivates calibration; it does not quantify the overhead of the browser collectors proposed here. Minimally observed and profiled executions will therefore be compared in matched blocks. Changes in timing, central processing unit (CPU) use, failure and fault activity will be measured, and failed or truncated captures will be retained. A browser trace is an observation generated under instrumentation, not independent evidence that a fault was active.

\section{Repeated Measurement and Experimental Validity}

Repeated visits support longitudinal comparison only when their conditions are recorded. Cache state, browser profile, server state, network and CPU conditions, session data, and workload order can alter a visit. WProf shows the value of decomposing browser load behavior and conditioning interpretation on workload and state; its historical Chromium results do not establish a modern repeat count or a protocol for this study \parencite{D568X6SQ}. Vesper's two-pass approach provides a browser-specific example of lighter measurement after heavier discovery. Its authors discuss possible differences between loads, but no different functional state was observed in their tested corpus. Vesper places heavy discovery before lighter measurement; the present study instead examines richer profiling after a lightweight original visit \parencite{HS3PKWFL}.

Web Execution Bundles (WebREC) provide a particularly relevant contrast: archiving an execution can support later analysis of the recorded visit without treating a new visit as equivalent. This is prior art for preserving original-execution evidence. It does not establish that the pilot's browser event buffer is feasible, covers the chosen performance endpoints, or is cheaper than a fresh diagnostic visit \parencite{ZZSL9IPU}. The cited arXiv v4 manuscript supports this distinction; targeted passages in the final proceedings paper corroborate it without establishing complete equivalence between editions. Lab measurements also have a different target from real-user monitoring (RUM); controlled interventions can support causal testing when their execution and intended effect are independently checked under declared conditions. A configured fault flag alone is insufficient. Such a corpus does not establish production prevalence or a field percentile.

Randomized order, explicit browser and fixture resets, repeated stable histories, chronological splits and records of actual state will be used to improve comparability. A new browser context isolates browser storage, but does not reset every server, host, or shared cache condition. A site-specific baseline can characterize earlier observations; it cannot alone determine why a particular visit was anomalous. Repeated visits are not independent websites; conclusions will be limited by the tested fixtures and conditions.

\section{Research Gap and Study Positioning}

Existing work establishes these mechanisms and several combinations of them: current browser metrics and attribution, browser instrumentation, selective or adaptive tracing, site-specific histories, recorded execution, and bounded retention. The proposed contribution is the narrower empirical comparison: whether delayed rich profiling correctly attributes an earlier browser regression episode compared with feasible evidence saved on the original visit, under common budgets and a fixed deadline, with independent verification of fault activity on each relevant visit.

The proposed gap remains a research question rather than proof that no equivalent exists. Existing lightweight attribution may already classify every selected cause, leaving little value for richer collection in this fault set. Closely related systems may also narrow the contribution after further comparison. The study will therefore assess added diagnostic value rather than assume an advantage for retained evidence. If a useful bounded original-event record cannot be collected, the comparison will be revised before the main study.

Fault persistence will be the principal condition examined, with follow-up delay and browser state treated as secondary factors. A correct explanation of the follow-up visit will be distinguished from a correct explanation of the original cause. Failures and abstentions will remain visible, and time, CPU, memory and stored bytes will be reported separately. These choices make the comparison testable while limiting conclusions to the browser, fixtures, faults and observation schedule actually evaluated.
