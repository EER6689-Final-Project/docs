## Abstract and scope

The authors investigate performance mutation testing (PMT): inserting source-code changes that preserve functional behavior while introducing performance degradation, then using those mutants to assess performance tests. They define seven performance-specific mutation operators and evaluate them in three real-world C++ programs. The study uses execution time as its performance property; it proposes that the approach could extend to other properties such as memory when suitable profilers are used, but does not test profiler accuracy or memory profiling.

## Outline Summary

- **Problem and objective:** Functional tests can miss performance regressions because functional correctness does not establish performance behavior. The paper asks whether source-level performance mutants can be defined and used to assess performance tests.
- **Approach and subjects:** The authors define seven operators from reported performance bug patterns, then apply them to Dolphin, TinyXML2, and XmlRPC++. They also compare traditional mutation operators. Mutants were manually injected and checked against compiler output for cases where compilation erased the mutation.
- **Evaluation procedure:** Existing functional test suites were adapted with timing assertions. The original program and each candidate mutant were each run 30 times per test case. The authors used a one-sided Mann–Whitney U test because execution-time data failed the Shapiro–Wilk normality test, and assessed significance at p-value thresholds 0.01, 0.05, and 0.1. Mutants causing timeouts were discarded. Live mutants at p < 0.1 received manual review (pp. 14–15).
- **Results reported by the authors:** Seven performance-specific operators were applied in the three programs. In total, 194 of 241 generated performance mutants (over 80%) were not detected by the accompanying functional tests. Only 42.7% of traditional mutants survived those suites as potentially valid PMT mutants. The authors interpret the performance mutants as promising for assessing performance tests, while noting that real-world effectiveness is not yet established (pp. 16–22, 25).
- **Author-stated future work:** Confirm results with a larger set of traditional operators, explore additional performance operators and domains, establish practical effectiveness through real case studies, improve automation, and investigate methods for detecting issues across non-functional properties (pp. 25–26).
- **Limitations and validity:** Mutants and live-mutant relevance were manually reviewed, so both steps can contain human error. Results come from three C++ programs and adapted functional test suites, use execution time only, and depend on the selected thresholds and 30-run procedure. The authors state that the effectiveness of PMT in practice and across domains remains an open question. This is evidence about test-suite fault-detection assessment, not a validation of profiler measurements against ground truth.
- **T1.5 relevance (inference):** PMT offers a possible controlled way to create known performance degradations for testing whether a profiler or its surrounding analysis pipeline notices a change. That adaptation is a project inference: the paper evaluates performance tests, not profiler sensitivity, accuracy, or agreement with an independent measurement method. Any profiler-validation use would need to specify the injected effect, target metric, and independent expected result.
- **Concise takeaway:** The paper demonstrates source-level performance mutants as candidates for evaluating performance tests in three C++ systems; it does not establish that a profiler correctly detects or quantifies those effects.
