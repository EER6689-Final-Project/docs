# Measurement Foundations for a Custom Browser-Based Web Performance Profiler

## Executive synthesis

As of **29 August 2026**, the current stable **Core Web Vitals (CWV)** are **Largest Contentful Paint (LCP)** for loading performance, **Interaction to Next Paint (INP)** for responsiveness, and **Cumulative Layout Shift (CLS)** for visual stability. Google’s current “good” thresholds are LCP ≤2.5 s, INP ≤200 ms, and CLS ≤0.1, normally assessed at the 75th percentile of page views. **First Input Delay (FID) ceased to be a Core Web Vital when INP replaced it in March 2024.** FCP, TBT, Speed Index, TTI, TTFB, memory measurements, network timings, and browser CPU/rendering counters are not Core Web Vitals. citeturn7search2turn7search0turn0search6

This distinction is more consequential than terminology suggests. Core Web Vitals were conceived primarily as **field-oriented user-experience outcome metrics**. LCP and CLS can also be measured meaningfully in controlled laboratory runs, while INP requires actual or scripted interactions; a navigation-only Lighthouse run therefore cannot directly measure INP and uses **Total Blocking Time (TBT)** as a laboratory diagnostic correlated with responsiveness rather than as an equivalent metric. Google explicitly warns that TBT is neither a Core Web Vital nor a field substitute for INP. citeturn7search2turn5search0

A rigorous profiler should consequently distinguish at least three kinds of measurements. The first are **user-centric outcome indicators** such as LCP, INP, CLS, FCP, and, in synthetic testing, Speed Index. The second are **mechanistic or diagnostic measurements** such as request timings, resource sizes, long tasks, JavaScript execution, style recalculation, layout, and paint activity. The third are **resource/state measurements**, such as JavaScript heap size, page-attributed memory estimates, DOM-node counts, document counts, and event-listener counts. These classes answer fundamentally different questions and should not be collapsed into a single undifferentiated notion of “performance.” W3C specifications themselves frame Paint Timing, Event Timing, Navigation Timing, Resource Timing, Long Tasks, and Server Timing as different observable phenomena rather than one global performance variable. citeturn14search12turn14search6turn14search9turn14search0

A second major conclusion is that **a browser profiler does not directly observe several quantities that developer terminology appears to imply**. TTFB is not “server processing time”: from a browser it is an end-to-end client-observed interval ending at `responseStart`, potentially incorporating redirects, cache/CDN behavior, connection establishment, and network transport. Server-internal processing can only be distinguished when the server explicitly supplies measurements, for example through `Server-Timing`. Similarly, Resource Timing's `transferSize` is not exact wire traffic: the specification deliberately uses a fixed 300-byte header approximation and special values for cache behavior. citeturn6search1turn14search0turn9view8turn14search6

Likewise, there is no standards-defined universal metric called “JavaScript execution time,” “rendering time,” “layout time,” or “painting time.” Chrome DevTools presents categories such as Scripting, Rendering, and Painting by interpreting Chromium trace events; examples include Evaluate Script, Function Call, Recalculate Style, Layout, Composite Layers, and Paint. Those are extremely useful diagnostic signals, but they are **Chromium instrumentation semantics**, not cross-browser Web Performance API metrics with the interoperability status of Navigation Timing or Resource Timing. citeturn15search2turn15search0turn16search11

The same caution applies to memory. `performance.memory` is non-standard and reports JavaScript-heap quantities whose scope can both under- and over-represent a page. The WICG `performance.measureUserAgentSpecificMemory()` proposal instead estimates memory attributable to a web application, including its workers and iframes, but requires cross-origin isolation and deliberately permits implementation-specific estimation and breakdown granularity. Chrome DevTools Protocol's `Runtime.getHeapUsage`, meanwhile, reports the JavaScript heap of the corresponding V8 isolate and explicitly states that it is not scoped to a particular runtime context. These measurements should therefore never be presented as interchangeable “page memory.” citeturn14search1turn14search10turn16search2

Construct validity is an equally important limitation. LCP does not claim to measure whether the most *important* content is ready; its specification explicitly characterizes LCP as a heuristic and acknowledges that it can be wrong, including when early interaction terminates observation before the eventual main content appears. CLS quantifies layout instability, not usability in general. INP measures the latency of a defined set of interactions, not scrolling, animation smoothness, or application correctness. Speed Index quantifies visual progression, not functional readiness. citeturn9view2turn5search0turn14search16

Empirical systems and QoE research reinforces this limitation. Kelton et al. found that conventional loading metrics poorly represented user-perceived page-load time and showed that visual attention matters; their later mobile work found that initial-viewport models inadequately represent mobile users who begin scrolling while loading. Netravali et al.'s Vesper study reported that existing loading metrics could under- or overestimate their explicitly functional notion of time-to-interactivity by 24–64%. More recent controlled and crowdsourced work by Wehner and colleagues found Core Web Vitals substantially less predictive of subjective web QoE than might be inferred from treating them as comprehensive UX measures. citeturn17search2turn23search17turn22search5turn22search2turn21search3

The strongest measurement claim a custom profiler can therefore make is not “we measure web performance” in a unitary sense. It can legitimately claim that it **observes specified browser events and state, derives explicitly versioned metrics from them, and characterizes several distinct dimensions of runtime performance under declared execution conditions**. Any stronger claim—especially one equating a synthetic score with real-user experience, client-side TTFB with server execution, TBT with INP, trace CPU categories with cross-browser standards, or heap size with total page memory—requires additional qualification. citeturn7search2turn6search0turn14search0turn16search2

## Metric evidence matrix

The table treats a measurement as **direct** when the browser exposes the relevant event, timestamp, counter, or trace interval as the immediate observation, and as **derived** when a profiler must aggregate, select, subtract, threshold, window, or otherwise transform lower-level observations. That distinction is conceptual rather than metaphysical: even “direct” browser entries depend internally on browser algorithms. High Resolution Time further permits user agents to reduce clock precision for security and privacy, so timestamps should not be described as inherently nanosecond- or even sub-millisecond-accurate observations. citeturn14search17

Two further qualifications follow directly from this matrix. First, **measurement units do not imply construct equivalence**: LCP, INP, FCP, TBT, SI and TTFB may all ultimately be represented in milliseconds, yet they measure different phenomena. Second, a value may be numerically derived from browser timestamps while still being conceptually user-centric: INP and LCP are examples of metrics whose intended constructs are outcomes even though their final values require algorithms over lower-level entries. citeturn8view1turn8view2turn14search17

## Corrected taxonomy and applicability

A useful taxonomy for the proposed profiler separates **outcomes**, **progress indicators**, **causal/diagnostic observations**, and **resource-state measurements** instead of placing every quantity under “loading metrics.”

| Measurement family | Appropriate members | What a profiler can legitimately say | What it should not imply |
|---|---|---|---|
| **Loading outcome / prominent-content visibility** | LCP | “Time at which the browser's LCP algorithm identified the final largest qualifying content candidate under this run's lifecycle.” | “Time when all content loaded,” “time when the page became useful,” or “time when the user perceived completion.” LCP is explicitly heuristic. citeturn9view2turn8view1 |
| **Initial visual appearance** | FCP | “First qualifying contentful paint after navigation.” | “Main content loaded.” citeturn9view0 |
| **Responsiveness outcome** | INP | “Near-worst latency of the qualifying interactions actually exercised/observed during the measured page lifecycle.” | “General interactivity” without specifying workload; scroll smoothness; response to interactions that never occurred. citeturn5search0turn8view2 |
| **Responsiveness diagnostics** | TBT, Long Tasks, Long Animation Frames, trace tasks | “Potential main-thread blocking under this controlled workload.” | “Measured INP” or “actual user input delay” when no interaction was executed. citeturn14search8turn7search2turn8view5 |
| **Visual stability** | CWV CLS; underlying LayoutShift entries | “Unexpected layout instability according to the specified Layout Instability/CWV aggregation.” | General design quality, animation quality, or complete visual UX. citeturn3search1turn3search2 |
| **Visual loading progression** | Speed Index, screenshot-based completeness curves | “Rate at which the recorded viewport visually approached its reference/final state.” | Semantic importance or functional readiness. citeturn14search16turn22search5 |
| **Client-observed request/network behavior** | Navigation/Resource Timing, TTFB, DNS/connect/TLS/request/response phases, encoded/decoded body size | “Browser-observed request and response timing/size according to W3C timing semantics.” | Server execution time, packet-level traffic, or exact cross-origin waterfall data. citeturn14search9turn14search6turn9view8 |
| **Server-attributed behavior** | `Server-Timing` | “Server-supplied named timing measurements for this request.” | Independently browser-verified internal server duration. citeturn14search0 |
| **Main-thread/browser execution diagnostics** | JavaScript evaluation/calls, GC, style recalculation, layout, paint, compositing, task time | “Chromium trace activity within explicitly defined trace categories and intervals.” | Portable Web Platform metrics unless an interoperable specification exists. citeturn15search2turn16search11 |
| **Resource footprint/state** | User-agent-specific memory estimates, JS heap, DOM nodes/documents/listeners | “Memory or structural state with stated API scope and observation time.” | A universal page-memory metric or direct user-experience score. citeturn14search1turn16search1turn16search2 |
| **Historical/retired metrics** | FID, TTI; older FMP/First CPU Idle metrics if encountered | “Legacy measurement reproduced for historical/tool-comparison reasons.” | Current Core Web Vital or preferred modern UX outcome. citeturn7search0turn14search2 |

This taxonomy also corrects the often-overused **lab-versus-field binary**. An underlying browser API can be usable in both environments while the *interpretation of the derived metric* remains field-centric. LCP and CLS illustrate this: both can be captured synthetically, yet CWV quality assessment is defined around real-user distributions. INP can technically be measured during a controlled DevTools session or automated interaction sequence, but the value is conditional on the interactions that occurred. Google therefore describes CWV as fundamentally field metrics while explicitly allowing local measurements as debugging evidence. citeturn7search2turn15search1

CrUX is not simply “the same metric measured more times.” It is a **real-user aggregate dataset drawn from eligible Chrome users and sufficiently popular/public origins and URLs**, with privacy filtering and normalization. Its page/origin values therefore represent a population statistic, not a replay of the conditions of a Lighthouse run. A profiler comparing its synthetic LCP of 1.8 s with a CrUX p75 LCP of 2.6 s is comparing a controlled observation with a distribution over heterogeneous real devices, networks, cache states, page states and users. citeturn6search0turn5search1

This distinction becomes especially important for responsiveness. A Lighthouse navigation audit has no genuine sequence of real user interactions and consequently cannot produce a representative INP; **TBT may diagnose main-thread conditions that often contribute to poor INP, but it is explicitly not INP**. Conversely, DevTools can display local INP as the developer interacts with a page because interactions are actually occurring. citeturn7search2turn15search1

There is also no defensible basis for treating the network and CPU families as independent causal dimensions. A slow resource can postpone script discovery; JavaScript can trigger further requests; long main-thread tasks can delay rendering after bytes have arrived; cached resources can eliminate network transfer without eliminating decode/layout/paint cost. A profiler should therefore describe these as **temporally related observations**, not assume that summing them yields a causal decomposition of page-load time. Navigation Timing, Resource Timing and Chrome's rendering traces expose different portions of this dependency structure. citeturn14search6turn14search9turn15search2

## Terminology, semantic non-equivalence, and construct validity

A central finding is that **identical names across tools do not guarantee identical reported objects**, even where they share a common lower-level specification.

| Common label | Why comparison is easily misinterpreted |
|---|---|
| **“LCP”** | The LCP API produces a sequence of candidate entries during one document lifecycle; a Web Vitals library derives a final page value; Lighthouse reports the value from one controlled audit; DevTools may show a local value for the currently exercised page; CrUX reports a real-user distribution/percentile. The underlying concept is related, but the statistical unit, workload, lifecycle, browser configuration and population are not the same. citeturn8view1turn15search1turn6search0 |
| **“CLS”** | Layout Instability exposes individual shift entries. Google's current Core Web Vital CLS applies session-window aggregation, whereas terminology in the incubated Layout Instability specification also discusses document-level cumulative scores. A naïve sum of all `layout-shift` values is therefore not necessarily current CWV CLS. citeturn3search1turn3search2 |
| **“INP” / “interaction latency”** | Event Timing entries are primitives; INP is an algorithm over grouped interactions. A local DevTools INP reflects the interactions just exercised, while CrUX's value describes a field population. Navigation-only Lighthouse cannot produce an equivalent INP and instead recommends TBT diagnostically. citeturn8view2turn5search0turn7search2 |
| **“TTFB” / “server response time”** | Browser TTFB is client-observed latency to response start. It does not separate origin application time from DNS, connection, TLS, cache/CDN, proxy or network effects. Server Timing is needed for explicit server-side phase attribution. citeturn6search1turn14search0 |
| **“Transferred bytes”** | Resource Timing `transferSize` deliberately includes a standardized 300-byte approximation and cache sentinel behavior; it is not exact TCP/QUIC/HTTP packet bytes. | **“JavaScript execution time”** | This is usually an aggregate over selected Chromium trace events rather than a W3C metric. Whether compilation, GC, microtasks, callbacks, extension execution or worker execution is included depends on instrumentation and aggregation definitions. Chrome has changed trace presentation/categories over time. citeturn15search2turn15search4 |
| **“Rendering time”** | Could mean style recalculation + layout, paint only, paint + compositing, all rendering-category trace events, main-thread rendering only, or end-to-end frame presentation. No unqualified value should be compared across profilers. citeturn15search2 |
| **“Page memory”** | `performance.memory`, `measureUserAgentSpecificMemory()`, CDP isolate heap, heap snapshots and browser-process memory have different scopes. They are not aliases for one measurement. citeturn14search1turn16search2 |
| **“DOM size”** | CDP's renderer DOM counters, a JavaScript traversal of the current document, an accessibility tree, and a diagnostic tool's DOM-complexity score are different objects. The scope must be stated. citeturn16search1 |
| **“Lighthouse performance”** | Lighthouse's **performance score** is itself a normalized weighted composite, not another raw timing metric. It therefore cannot be interpreted as a physical measurement scale. citeturn14search5 |

### Construct validity

The metrics also differ in **what latent aspect of user experience they plausibly operationalize**.

LCP operationalizes a notion of prominent content visibility by selecting the largest eligible viewport content. That is a defensible proxy for loading experience, but it does not establish that the selected content is the user's task-relevant content. The LCP specification explicitly describes the mechanism as heuristic and discusses error cases, which is unusual but valuable evidence against treating LCP as a literal measurement of “when the page was useful.” citeturn8view1turn9view2

FCP is still narrower: it provides evidence that the page has begun to render meaningful DOM content, but a page can produce an excellent FCP by rapidly painting a header or loading indicator while its principal content remains absent. LCP was introduced precisely because milestones such as FP/FCP do not reliably correspond to the point at which the page's main content appears. citeturn9view0turn8view1

INP has stronger face validity for responsiveness than FID because it spans the full latency to presentation and considers interactions across the page lifecycle rather than merely the input delay of the first event. Yet INP is still conditional on the **interaction distribution**. A page containing an extremely slow rarely used control can receive a good run-level INP if that control is never exercised; another test sequence may expose it. Conversely, a workload that systematically triggers an expensive feature will measure a different operational behavior. citeturn7search0turn5search0

CLS measures a different phenomenon altogether. A layout can remain geometrically stable while being visually confusing or slow, and a layout shift can be deliberately caused by user input and therefore excluded from CWV CLS. A low CLS must consequently be read as evidence of low *unexpected geometric instability according to the algorithm*, not evidence of an otherwise good UI. citeturn3search1turn3search2

Speed Index is particularly illustrative of the difference between measurement and perception. It mathematically rewards rapid visual completion of the viewport, but does not know which pixels the user attends to. Kelton et al.'s gaze work found poor correspondence between traditional page-load metrics and user-perceived completion and demonstrated that user attention concentrates on particular regions. Gao, Dey and Ahammad likewise studied perceived above-the-fold speed through large-scale crowdsourcing, reflecting the broader observation that visual completion and perceived completion are related but not identical constructs. citeturn17search2turn23search2turn23search10

The same issue is even stronger for **interactivity**. Netravali, Nathan, Mickens and Balakrishnan defined Ready Index around both viewport visibility and availability of the JavaScript/DOM state supporting interactive elements; their Vesper experiments found that prior page-load metrics could under- or overestimate this functional readiness by 24–64%. Thus two pages with similar Speed Index—or even similar LCP—can have very different functional readiness. citeturn22search5

Mobile behavior further weakens a fixed-viewport interpretation of loading quality. Kelton et al.'s 2020 MobileHCI study explicitly found that conventional user-PLT methods focused on the initial viewport were ill suited to mobile behavior because users can begin scrolling while content is still loading; their model incorporated activity across multiple viewports. citeturn23search17

It follows that **two sites can have identical values for one metric and markedly different UX without any measurement error occurring**. Two pages with LCP = 2.0 s may differ radically in INP, CLS, content relevance, animation fluidity, post-load network activity or memory pressure. Even two pages matching on LCP, CLS and INP can differ in accessibility, application correctness, task completion, scroll performance, energy usage and content quality, because none of those are constructs defined by the three CWV algorithms. Google itself describes CWV as three *facets* of experience rather than a complete UX ontology. citeturn21search15turn21search4

## Contradictory evidence and unresolved debates

The most important apparent contradiction is between the **usefulness of Core Web Vitals as standardized engineering signals** and their **limited validity as holistic predictors of subjective QoE**. Google describes CWV as real-world signals reflecting critical user-centric outcomes and recommends their broad adoption. citeturn21search15turn21search4 Yet Wehner, Amir, Seufert, Schatz and Hoßfeld's 2022 QoMEX experiments found lower predictive value for CWV than expected, and the expanded 2023 study by Wehner, Seufert, Schatz and Hoßfeld again concluded that conventional loading-time effects remained highly important to subjective web QoE. These findings do not show that CWV are invalid; rather, they reject an interpretation of CWV as a sufficient model of total subjective experience. citeturn22search2turn23search8turn21search3

There is no genuine standards contradiction in LCP's current status, but there is an instructive tension: LCP is a **stable Core Web Vital while the underlying W3C specification remains a Working Draft and explicitly labels the algorithm heuristic and potentially error-prone**. “Stable Web Vital” is therefore a Google metric-lifecycle designation, not the same thing as W3C Recommendation maturity or proof that the construct perfectly captures perception. citeturn14search12turn9view2turn7search2

CLS presents a more concrete terminology problem. The Layout Instability work defines the underlying shift primitive and document-level concepts, but Google's current CWV CLS uses the maximum session-window aggregation introduced to prevent indefinitely long-lived pages from accumulating unbounded scores. Anyone implementing “CLS = sum of all layout-shift scores” from the primitive API can consequently produce a different number from current CWV CLS while believing the same metric name has been implemented. citeturn3search1turn3search2

The replacement of FID by INP demonstrates that metric validity is not static. FID was a Core Web Vital but was judged too narrow because it covered only first-interaction input delay. INP broadened the construct to interaction latency over page lifetime, including processing and presentation components. A profiler whose schema hard-codes “Core Web Vitals = LCP, CLS, FID” would already be conceptually obsolete. citeturn7search0turn8view2

TTI demonstrates a related issue on the synthetic side. Lighthouse retired it because sensitivity to outlier network requests and long tasks generated high variability. TBT remains useful because it captures blocking behavior during load, but Google explicitly treats it as a laboratory diagnostic/proxy rather than as the user outcome itself. The history cautions against treating any current derived heuristic as permanent merely because a major tool reports it. citeturn14search2turn14search8turn7search2

There is also an unresolved **scope problem for modern long-lived applications**. Traditional Navigation Timing begins with a document navigation, whereas single-page applications may execute substantial route transitions without a new hard navigation. CrUX documentation has historically noted the difficulty of attributing SPA experiences to subsequent route URLs because platform navigation boundaries did not expose those transitions in the same manner as full navigations. Work on soft-navigation measurement is evolving, so a 2026 profiler should not silently equate “page lifecycle” with “user-visible route lifecycle.” citeturn6search0

Cross-origin content creates another unresolved practical mismatch between what Chrome internally knows and what page JavaScript may be permitted to observe. Resource Timing deliberately suppresses sensitive cross-origin information without the necessary opt-in, and performance APIs impose frame/origin boundaries for privacy. Consequently, a browser-internal trace, CDP client, page-injected PerformanceObserver, and CrUX aggregation may have different observability even when they nominally report the same class of phenomenon. citeturn14search6turn9view9turn9view10

Memory remains even less settled. The WICG memory proposal explicitly exists because traditional JS-heap reporting can both overestimate and underestimate a page's actual memory footprint. It permits estimated results and implementation-specific attribution. This means there is presently no standards-backed scalar that supports the unconditional statement “this URL uses X MB of browser memory.” A defensible statement must name the measurement scope. citeturn14search1turn16search2

Finally, the literature does not support a single universal objective function for web loading. Gaze-based work emphasizes attention; Vesper emphasizes visual plus functional readiness; MobileHCI work incorporates scrolling behavior; QoMEX work questions how strongly CWV predict overall QoE; Google's Web Vitals intentionally favors a small, operationally tractable set of broadly applicable signals. These are better understood as **different operationalizations of partly overlapping constructs** than as competing attempts to measure one self-evident ground-truth quantity called “web performance.” citeturn17search2turn22search5turn23search17turn22search2

## Implications for a custom browser profiler

The following separates propositions strongly grounded in specifications/tool documentation from design inferences that follow from those findings but are not themselves mandated by the literature.

| Implication | Evidential status | Rationale |
|---|---|---|
| **Store raw performance entries or trace primitives separately from derived metrics.** | **Literature/specification-supported.** | LCP, CLS, INP and TBT are algorithms over lower-level paint, shift, event and task observations. Preserving primitives allows algorithm revisions to be audited rather than confusing collection with interpretation. citeturn8view1turn3search1turn8view2turn14search8 |
| **Version every derived metric definition.** | **Strong researcher inference from documented metric evolution.** | CLS aggregation changed; FID was replaced by INP; TTI was retired. A value named only `"cls": 0.12` is insufficient provenance for longitudinal research. citeturn3search2turn7search0turn14search2 |
| **Represent `metric_name`, `metric_definition_version`, browser/version, collection mechanism, lifecycle boundary and workload as separate metadata.** | **Researcher inference.** | The evidence shows that same-name values can differ because of lifecycle, tool and population rather than arithmetic error. This schema would make those conditions explicit. citeturn6search0turn15search1 |
| **Do not expose TBT as “interactivity” without the word laboratory/diagnostic.** | **Literature-supported.** | Google explicitly distinguishes TBT from field INP and treats it as a lab diagnostic/proxy. citeturn7search2turn14search8 |
| **Do not expose browser TTFB as “server processing time.”** | **Specification-supported.** | Browser timing cannot decompose server routing/application time; `Server-Timing` exists specifically to communicate such internal metrics. citeturn14search0turn6search1 |
| **Expose Resource Timing byte properties by their exact names rather than a generic `network_bytes`.** | **Specification-supported.** | `transferSize`, `encodedBodySize` and `decodedBodySize` have materially different semantics, and `transferSize` is not exact wire bytes. citeturn9view8turn14search6 |
| **Separate standards-based browser APIs from Chromium-only/CDP measurements in the API schema.** | **Literature/specification-supported; schema separation is inference.** | Navigation, Resource, Paint and Event Timing have Web Performance specifications; Chrome trace categories and CDP DOM/heap counters are browser-specific instrumentation. citeturn14search12turn16search1turn16search2 |
| **Treat JavaScript, style, layout and paint totals as interval-defined diagnostic aggregates, not universal metric names.** | **Tool-documentation-supported.** | DevTools obtains these concepts from trace event categories. The aggregation window and included event classes must therefore be part of the definition. citeturn15search2 |
| **Label memory values with scope, e.g. `ua_specific_page_memory_estimate`, `v8_isolate_heap_used`, rather than `memory_usage`.** | **Strong researcher inference from API semantics.** | The available memory APIs explicitly measure different scopes. citeturn14search1turn16search2 |
| **Treat DOM node/document/listener counts as explanatory state variables.** | **Literature-supported classification; causal use is inference.** | CDP exposes them as counters; no cited standard defines them as user-centric performance outcomes. citeturn16search1 |
| **For lab INP, record the exact interaction script and state transitions alongside the value.** | **Strong researcher inference.** | INP is computed only from interactions that occur; without workload provenance, two lab INP values do not necessarily measure comparable behavior. citeturn5search0turn8view2 |
| **Do not compare a synthetic run directly with a CrUX percentile as if they were repeated samples from one experiment.** | **Literature-supported.** | CrUX is an aggregate real-user population subject to eligibility/privacy rules; laboratory runs operate under controlled device/network/browser/workload conditions. citeturn6search0turn7search2 |
| **Preserve browser and profiler versions with traces.** | **Strong researcher inference from implementation evolution.** | Chrome's trace presentation/categories and Lighthouse metric set have changed, including removal of TTI and changes to trace-category presentation. citeturn14search2turn15search4 |
| **Avoid collapsing heterogeneous metrics into an unexplained scalar “performance score.”** | **Literature-supported concern; API-design consequence is inference.** | Lighthouse's own score demonstrates that any such scalar requires explicit normalization distributions and weights; it is not a direct physical quantity. citeturn14search5 |
| **Where possible, report uncertainty/distribution across repeated controlled runs rather than only one number.** | **Researcher inference strongly motivated by documented variability.** | TTI's retirement because of high variability and the general lab/field distinction show that single observations can be unstable and environment-dependent. citeturn14search2turn7search2 |

A particularly useful architectural implication is to distinguish **observation**, **normalization**, and **interpretation**. Observation would retain native timestamps, entries, counters and trace events. Normalization would transform units and identifiers without changing metric semantics. Interpretation would implement named/versioned algorithms such as CWV CLS session windows, INP interaction selection, TBT blocking sums, Speed Index visual progression, or custom aggregate CPU categories. This three-layer split is a **researcher inference**, but it follows directly from the fact that the standards expose primitives while several widely used metrics are higher-level algorithms over those primitives. citeturn3search1turn8view2turn14search8

“Normalized” should therefore **not** mean making unlike measurements appear comparable. Converting every duration to milliseconds is harmless unit normalization; transforming a CrUX p75 LCP, one Lighthouse LCP, one local DevTools LCP and a raw `LargestContentfulPaint` candidate into a common field called `lcp_ms` without provenance would erase essential semantics. citeturn6search0turn15search1turn8view1

For similar reasons, the profiler should be careful with causal language. A trace showing 600 ms of script activity before LCP establishes temporal work observed before LCP; it does not by itself prove that eliminating all 600 ms would improve LCP by 600 ms. Browser pipelines contain dependencies, parallelism and idle/blocked intervals. The evidence surveyed here supports **measurement and association**, while causal attribution requires a separate experimental design that is outside the requested measurement-foundations scope. citeturn15search2turn14search6
