# Monitoring Novelty Cross Reference

**Reviewed:** 2026-10-31. **Question:** does website-specific history with adaptive browser profiling leave a defensible research gap after comparison with the repository papers and current solutions?

**Researcher decision after this review:** proceed with **Reliability of Delayed Browser Performance Diagnosis**. The [Research Plan](<Research Plan.md>) records the selected direction. This review's qualifications about novelty, source access and untested methods still apply.

**Source-check update:** the [2026-10-31 direct review](<../Research Archive/Review Artifacts/2026-10-31 Decision-Critical Source Checks/README.md>) resolves WMF's earlier access discrepancy and the five named closest-work identity mappings. Its [appraisals](<../Research Archive/Review Artifacts/2026-10-31 Decision-Critical Source Checks/Source Appraisals.md>) supersede earlier access wording only for the checked claims/editions. LMAT controller details, Shahedi's final journal text and Paradyn's exact journal passage equivalence retain explicit bounds. The gap remains provisional.

**Finding:** the broad idea is already substantially covered. Website histories, regression alerts, adaptive instrumentation, selective trace retention and seeded performance faults are established. The strongest candidate is a narrower **empirical study of delayed browser diagnosis**: when a verified short-lived problem occurs during lightweight monitoring, determine whether a subsequent detailed visit identifies the original cause as reliably as evidence retained from the original visit, and at what total measurement cost. This is a possible browser-specific validity/coverage contribution, not an invention of adaptive profiling or proof that no equivalent study exists.

The [previous monitoring direction](<../Research Archive/Continuous Website Performance Monitoring Research Direction.md>) remains useful as a system design. Its novelty claim should be narrowed using the evidence below. Website-specific baselines become the detection/context infrastructure; the scientific endpoint is the reliability of diagnosis across different visits.

The proposed gap is an inference from that chain, not an author-stated joint conclusion.

## The strongest residual question

**Working title:** Reliability of Delayed Browser Performance Diagnosis.

**Research question:** For persistent and intermittent website performance regressions, when does a detailed follow-up visit identify the independently verified cause of the original anomalous visit, compared with retaining original-visit evidence under matched total monitoring costs?

This targets a hidden assumption in the previous proposal: the detected problem will still exist, with the same cause, when richer profiling begins. A history can identify an unusual symptom; a later trace can explain the later execution. Those facts alone do not establish the cause of the original symptom.

For example, a first visit may be slow because a designated script performs unusually expensive work. On the follow-up visit that branch may not run, or another resource may be slow for a different reason. A diagnosis of the second visit can be correct for that visit and still be misleading when attached to the first alert. Controlled examples must include such same-symptom/different-cause cases rather than treating detection of any slow metric as correct attribution.

### Contributions that could emerge

1. **An empirical validity boundary:** identify how fault persistence, follow-up delay and browser state affect correct original-episode diagnosis and unavailable evidence. A conditional failure result can be the contribution; algorithm superiority is not required.
2. **A tested collection decision, if the evidence supports it:** determine when legitimate cheap attribution, bounded original-event recording or a fresh rich visit is worthwhile within the declared budget. Test against simple schedules before proposing a learned policy.
3. **A reusable episode-level benchmark:** link site/profile histories to independently verified original/follow-up fault activity, capture loss and attribution outcomes. Its contribution is the evaluation question and demonstrated value, not merely a collection of traces.

These are potential outputs of one focused study. The current evidence does not justify calling any one a first, universally better or already novel method.

## A decisive feasible comparison

Use owned or authorized controlled deployments with a fixed safe journey, pinned browser and a small fault/profile subset. A fixture controller records the intended intervention and an independent execution check verifies that it actually occurred. Labels remain evaluator-only. The policy receives only predeclared observations, context and past history; fault schedules or revealing deployment labels must not leak into its decisions.

| Strategy | What evidence it can use | Cost that must be counted |
| --- | --- | --- |
| Legitimate lightweight metrics and available attribution | Signals recorded on the original visit using existing low-cost facilities. | Initial instrumentation, history construction and all sampling attempts. |
| Lightweight alert followed by rich new visit | Detailed evidence from a subsequent execution. | Original scan, trigger/confirmation work, queue delay, retries and rich rerun. |
| Bounded original-event capture with triggered retention | Only events actually recorded before/during the original episode and not lost from the buffer. | Continuous capture/serialization, memory, drops, retention and export; writing files only on alerts does not make collection free. |
| Periodic or random rich capture | Original-visit details only when the schedule selects that visit. | All scheduled captures, including visits without faults. Match complete budgets, not just retained trace sizes. |
| Always-rich capture | A diagnostic coverage/cost reference, not independent cause truth. | Full capture and any perturbation. It is a ceiling comparator when not budget-comparable. |

An original-event buffer is a **feasibility-gated comparator**, not a promised implementation: identify exact browser-supported event types, whether they contain the evidence required by the chosen attribution task, startup requirements, lifecycle limits and measured loss. If a feasible buffer cannot provide those endpoints, compare available original-visit attribution with reruns and fixed capture, narrow the claim accordingly, and do not call retained logs a full original trace. A full WebREC or Hindsight port is not a prerequisite for a student study.

Include stable controls, persistent faults, intermittent/one-visit faults, nuisance condition changes, and different causes producing similar measured symptoms. Verify active fault class separately on the original and follow-up visits. Reproducing a symptom is not proof that the same cause recurred. Define externally controlled episode schedules or matched blocks so additional diagnostic visits do not silently change the comparison's fault opportunities.

The cause oracle is the independently verified intervention. **A detailed trace remains a reference observation:** it can omit information, misattribute events or perturb the workload, so it must not supply its own truth label. Record capture settings and a small common verification probe in every arm, and estimate incremental changes under the stated conditions rather than exact unobserved execution.

### Outcomes and safeguards

The primary outcome should include **all verified regression episodes**: the fraction correctly attributed to the original fault class within a declared diagnosis deadline and complete monitoring budget. Report missed triggers, unsuccessful reruns, unavailable evidence, budget-exhausted cases and explicit abstentions separately rather than removing them.

Also report initial detection delay, false alarms per stable/nuisance time or eligible observation, original-episode misattribution, recurrence on follow-up, conditional diagnostic performance when a fault is present, capture loss, and total collection cost. An abstaining method can appear perfectly precise while diagnosing almost nothing; show diagnostic coverage beside conditional precision and false-attribution rates.

Train site/condition baselines on earlier designated stable data, tune on a separate period and evaluate later deployments. Hold out fixture templates/instances before tuning. Keep the detection logic fixed across capture-policy arms when isolating the capture decision; assess personalized versus generic detection in a separate ablation. Baseline updates must not learn away persistent regressions. Dependence, repeated alarms and multiple endpoints require a justified analysis rather than repeated unadjusted tests.

This is deliberately smaller than building a universal anomaly detector, a tracing engine and a production monitoring service together. It preserves the assigned profiler/API and dashboards as engineering outputs while keeping one primary scientific question.

## What would rule out the contribution

| Finding | Consequence |
| --- | --- |
| An existing browser study already evaluates equivalent original/follow-up attribution, fault lifetimes, evidence policies and complete costs. | The claimed gap closes; reproduce or identify a genuinely different unresolved endpoint. |
| Existing cheap attribution identifies the selected original causes as well as richer policies. | Deep escalation has not demonstrated added diagnostic value for those tasks. |
| A periodic/random rich schedule matches the adaptive policy at the same cost and delay. | Reject superiority of the adaptive policy; report the simpler strategy and measured boundary. |
| Faults vanish before rerun or a different fault replaces them. | Report non-reproduction or false linkage; do not attach the follow-up cause to the earlier alert as established fact. |
| Buffer/archive methods solve the task within the same feasible budget. | A rerun-based solution lacks benefit; any remaining result must concern an uncovered constraint or validity boundary. |
| Results depend on oracle labels visible to the policy, dropped failures or contrived fixtures unrelated to the stated workload. | The evaluation cannot support the proposed claim. Repair the design before interpreting performance. |

## Recommendation and source status

Keep the website-specific dataset, but organize it around **episodes and evidence provenance**, not only a rolling table of metric values. Narrow option 1 to the reliability of delayed diagnosis and compare collection choices; use option 2 as the fixed-policy benchmark if a novel adaptive policy is not supported. This is the most defensible candidate emerging from the local papers and web comparison, with novelty still provisional.
